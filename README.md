# GitHub 零基础实践指南

一份给普通人的 GitHub 入门教程。

你不需要先学会编程，也不需要先理解一堆命令。先把 GitHub 当成一个可以发现、使用、修改和分享数字作品的公共空间，再逐步学会协作。

[打开可视化教程](./docs/index.html)

## 新增：Novel Forge 小说写作工程系统

这个仓库现在同时提供一套可复用的中文小说写作工作流。它适合用来做
选题拆解、故事设定、章节规划、候选稿生成、连续性检查、情绪审稿、自然
度修订和长期状态维护。

它不会假装“重新训练”底层模型，也不承诺完美小说、100%过签或必然爆款。
它做的是把容易丢失的上下文变成文件，把“写得像不像好小说”拆成可以
反复检查的约束，让同一个 AI 在同一个项目里更稳定、更容易返工和持续
改进。

### 小说系统的核心闭环

```text
项目上下文
    -> 正史与状态读取
    -> 读者承诺与情绪合同
    -> 章节契约
    -> AI 候选稿
    -> 连续性 / 情绪 / 自然度审查
    -> 确定性质量检查
    -> 人工接受或返工
    -> 更新正史、钩子账本与回报账本
```

### 第一次使用

1. 阅读 [`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md)，填写题材、读者承诺、
   主角欲望、核心矛盾和金手指边界。
2. 阅读 [`AGENTS.md`](./AGENTS.md)，确认候选稿、正史、审稿和安全边界。
3. 复制 [`templates/story-bible.json`](./templates/story-bible.json) 和
   [`templates/chapter-brief.md`](./templates/chapter-brief.md)，为具体项目
   建立故事圣经与第一章契约。
4. 使用 [`prompts/`](./prompts/) 中的提示词按阶段工作，不要让一次长对话
   同时承担架构、写作、审稿和定稿。
5. 写候选稿后运行：

```bash
python tools/validate_story_state.py
python tools/validate_emotion_plan.py
python tools/novel_quality_audit.py --path path/to/chapter.md --fail-on P1
python -m unittest discover -s tests -v
```

### 目录说明

| 目录或文件 | 用途 |
| --- | --- |
| `PROJECT_CONTEXT.md` | 项目入口、读者承诺、世界规则和边界 |
| `.novel/novel-state.json` | 机器可读的正史状态入口 |
| `.novel/hook-ledger.json` | 伏笔、悬念、回收路径账本 |
| `.novel/payoff-ledger.json` | 读者承诺、局部回报和后续新问题账本 |
| `.novel/character-voiceprint.md` | 角色声音和行为差异 |
| `templates/` | 故事圣经、章节契约、情绪计划、审稿报告等模板 |
| `prompts/` | 架构、规划、候选写作、审稿、自然度和接受提示词 |
| `tools/` | 不依赖外部服务的状态校验和文本风险审计 |
| `docs/QUALITY_GATES.md` | 分层质量门和五人智囊审查框架 |
| `docs/market-gate.md` | 榜单证据状态、假设和最小验证实验 |
| `.github/workflows/quality.yml` | 推送和 PR 时运行的确定性检查 |

### 这套系统怎样让写作更稳

- **记忆不靠聊天窗口**：项目上下文、状态、正史和交接文件可以回查。
- **金手指有边界**：要求记录早期端倪、能力、硬限制、代价和失败方式。
- **爽点不靠大声**：每章要求目标、阻力、选择、代价、局部回报和新状态。
- **伏笔不靠堆数量**：每个钩子要记录读者问题、角色认知、触发条件和回收
  路径。
- **去 AI 腔有证据**：审计器只报告元话语、占位符、机械句式和导游式说明
  风险，最后仍由人工结合语境判断。
- **市场结论有闸门**：当前仓库明确记录 `rank_scout_status=data_required`，
  没有当前授权榜单时不编造“当下最火”的结论。
- **候选与正史分离**：AI 可以提出选项，但只有接受后的内容才能更新状态和
  账本。

### 使用边界

本仓库提升的是写作流程、项目记忆、审稿质量和迭代稳定性，不是模型权重
训练器。它不能证明作品一定过平台初筛、一定获得流量、一定像真人写作，
也不能替代作者对事实、版权、许可证和最终文本的判断。不要用它复制受版权
保护的原文或模仿在世作者的可识别文风。

## 你会学会什么

- 看懂 GitHub 仓库页面的常见按钮
- 找到适合自己的开源项目
- 判断一个项目是否值得下载和使用
- 分清 `Release`、`Download ZIP`、`Clone` 和 `Fork`
- 理解 `Commit`、`Branch`、`Pull Request` 和 `Tag`
- 用 AI 辅助创建 README、检查命令和整理 Issue
- 把自己的小项目整理成一个可以分享的开源仓库

## 先记住一句话

GitHub 不是只有程序员才能进入的代码仓库。

它更像一个公开的数字工作台：

1. 你可以拿走别人公开分享的项目来使用。
2. 你可以在遵守许可证的前提下修改它。
3. 你可以把自己的作品整理出来，接受反馈并持续更新。

## 30 分钟第一次实践

如果你只想马上开始，可以按下面的顺序走一遍：

1. 注册 GitHub 账号并完成邮箱验证。
2. 搜索一个明确的需求，例如 `windows pdf tool`。
3. 打开 3 个候选仓库，查看说明文档、最近更新、许可证和发布页面。
4. 优先下载 `Release` 中适合自己系统的安装包。
5. 记录你遇到的一个问题，不要直接把密码、Token 或个人隐私发到 Issue。
6. 如果你有自己的小项目，先建立一个私有仓库，确认没有敏感信息后再改为公开。

这次实践的目标不是把所有按钮都学完，而是完成一次完整的“发现 -> 判断 -> 使用”。

## 一、GitHub 到底是什么

GitHub 是基于 Git 的代码托管与协作平台，也是全球开源项目的重要聚集地。

对零基础用户来说，可以先把它理解成三层：

| 层次 | 你可以把它理解成 | 你能做什么 |
| --- | --- | --- |
| 项目展示 | 一个项目的主页 | 看说明、截图、版本和讨论 |
| 文件仓库 | 项目的文件柜 | 下载文件、查看历史、追踪变化 |
| 协作空间 | 一个公开工作台 | 提问、提建议、提交修改 |

GitHub 的核心价值不是“收藏很多项目”，而是让作品可以被使用、讨论、修改和继续维护。

## 二、注册与界面

### 注册时需要什么

通常需要：

- 邮箱
- 密码
- 用户名
- 邮箱验证

注册页面、验证方式和可选服务可能会随平台调整。遇到额外选项时，先读清楚用途，不需要的服务不要为了赶进度随手勾选。

### 英文界面怎么办

建议保留英文按钮名称，同时使用以下辅助方式：

- 浏览器自带翻译
- 浏览器页面搜索
- GitHub 官方帮助文档
- 自己整理一张常用词对照表

不要只依赖汉化脚本。界面变化后，原生按钮名称仍然是最稳定的搜索线索。

常用词：

| 英文 | 含义 |
| --- | --- |
| Repository / Repo | 仓库 |
| Code | 项目文件和代码入口 |
| Issues | 问题、提问和建议 |
| Pull requests | 修改申请 |
| Actions | 自动化任务 |
| Releases | 发布版本 |
| Settings | 仓库设置 |
| Public | 公开 |
| Private | 私有 |

## 三、五种找到好项目的方法

### 1. 目标明确：直接搜索

把“我想要什么”写成几个英文关键词，再补充平台、格式或用途。

例子：

```text
windows pdf tool
open source screen recorder
markdown editor mac
python image compressor
```

搜索结果出来后，不要只打开第一个项目。至少比较 3 个候选仓库。

### 2. 需求明确但项目名未知：使用组合关键词

常见的辅助词：

- `free`：免费
- `open source`：开源
- `awesome`：整理好的优质资源清单
- `windows`、`macos`、`linux`：目标系统
- `cli`、`desktop`、`web`：使用形态
- `self-hosted`：自己部署

例如：

```text
awesome self-hosted photo
free open source pdf windows
```

`awesome` 结果常常是资源合集，不一定是可以直接安装的单个软件，要继续点进具体项目核验。

### 3. 需求模糊：让 AI 帮你整理搜索词

不要只问 AI“推荐一个最好的项目”。更好的问法是让它先帮你拆需求：

```text
我使用 Windows，想找一个开源语音转文字工具。
要求：支持中文、最好有图形界面、可以离线运行、最近仍在维护。
请给出候选项目，并逐项列出：
1. 是否真的支持 Windows；
2. 是否支持中文；
3. 是否需要联网；
4. 最近一次发布或提交时间；
5. 许可证；
6. 安装难度；
7. 可能的隐私风险。
不要只根据 Star 数量下结论。
```

AI 给的是候选清单，不是事实证明。最终仍要回到项目页面核对。

### 4. 没有明确想法：看 Trending

Trending 适合发现趋势和新项目，可以按时间范围、语言等条件观察。

但“热门”不等于“适合你”。看到项目后仍要检查：

- 它解决的是什么问题
- 你的系统是否支持
- 是否有可用版本
- 文档是否能看懂
- 是否仍然维护

### 5. 通过外部渠道发现项目

还可以从以下地方获得线索：

- 技术社区
- 作者博客
- 公开视频或文章
- 开源项目合集
- 朋友推荐

外部推荐只负责帮你发现项目，下载和使用前仍要回到 GitHub 原仓库，避免拿到篡改包或过时链接。

## 四、如何判断一个项目值不值得用

### Star 只能当信号

Star 可以反映关注度，但不能单独证明质量，也不能保证安全。

建议同时检查：

| 检查项 | 你要看什么 |
| --- | --- |
| README | 能否看懂用途、安装和使用方法 |
| 最近更新 | 是否还有维护迹象 |
| Releases | 有没有适合你系统的正式版本 |
| Issues | 问题是否有人回复，重复问题是否长期无人处理 |
| License | 是否允许你的使用方式 |
| 安全性 | 是否要求关闭安全软件、执行陌生脚本或输入密钥 |
| 兼容性 | Windows、macOS、Linux 和 CPU/GPU 要求是否匹配 |
| 下载来源 | 是否来自原作者仓库或可信发布渠道 |

100 个 Star、1 万个 Star 都只是参考线，不是“靠谱证明”。Star 很少的新项目可能很有价值，Star 很多的项目也可能已经停止维护。

### 仓库页面怎么看

一个仓库地址通常包含：

```text
github.com/用户名/项目名
```

仓库可以是：

- `Public`：公开，任何人都可以看到
- `Private`：私有，只有授权成员可以访问

常见按钮：

| 按钮 | 作用 |
| --- | --- |
| `Code` | 查看文件、复制仓库地址、下载 ZIP |
| `Issues` | 提交问题、提问、提出功能建议 |
| `Pull requests` | 查看或提交修改申请 |
| `Watch` | 订阅项目动态 |
| `Star` | 收藏并表达支持 |
| `Fork` | 在自己的账号下复制一份仓库 |
| `Releases` | 查看作者发布的可下载版本 |
| `Actions` | 查看自动化构建、测试和发布任务 |

## 五、GitHub 的核心工作原理

可以把多人协作想成装修一套房子：

| GitHub 概念 | 装修类比 | 实际作用 |
| --- | --- | --- |
| 默认分支 | 主施工方案 | 项目被大家默认使用的主线 |
| Commit | 一次施工记录 | 保存一组具体改动 |
| Branch | 一套独立施工方案 | 在不影响主线的情况下开发 |
| Pull Request | 申请验收 | 请求把改动合并到目标分支 |
| Tag | 完工留档 | 标记一个稳定版本 |

### 默认分支不一定叫 `main`

很多项目使用 `main`，也有项目使用其他名称。看到教程里的 `main` 时，把它理解为“项目主线”即可，实际操作以仓库页面显示的分支名为准。

### Commit：保存一次有意义的变化

一次 Commit 最好只解决一个清楚的问题，例如：

```text
修复 Windows 安装说明
增加中文使用示例
更新依赖版本
```

不要把几十个互不相关的修改塞进一个没有说明的 Commit。

### Branch：隔离修改

常见命名方式：

```text
fix/修复内容
feat/新增功能
docs/文档修改
refactor/代码重构
```

这是团队约定，不是 GitHub 强制规则。重点是让别人一眼看懂这条分支要做什么。

### Pull Request：让修改进入项目

Pull Request 不是“提交后一定会被合并”。原作者可能：

- 直接合并
- 要求补充测试或修改说明
- 暂时搁置
- 拒绝这次修改

这是正常的协作过程。好的 PR 通常包含：问题背景、修改内容、测试方式、截图或复现步骤。

### Tag 与版本号

项目常用类似下面的版本号：

```text
v3.1.4
```

很多项目会按“主版本、功能版本、修订版本”的方式表达变化，但这是一种常见约定，不是 GitHub 的硬性规定。具体含义要以项目自己的发布说明为准。

## 六、四种下载与使用方式

### 1. 下载 Release：想直接用软件

适合普通用户。优先找项目的 `Releases` 页面，选择与你的系统匹配的文件：

- Windows 常见 `.exe`、`.msi`
- macOS 常见 `.dmg`、`.pkg`
- Linux 可能是 `.AppImage`、`.deb`、`.rpm` 或压缩包

下载后先看发布说明和校验信息。不要因为文件名像安装包，就跳过安全检查。

### 2. Download ZIP：临时查看源代码

适合：

- 想快速浏览文件
- 想看某个固定时刻的代码
- 当前不准备长期参与开发

ZIP 通常不会自动记录你与原仓库的同步关系。

### 3. Clone：长期在本地使用或修改

Clone 是把远程仓库复制到本地电脑。适合：

- 长期修改
- 运行项目
- 保存 Commit
- 跟随原仓库更新

Git 命令示例：

```bash
git clone https://github.com/用户名/项目名.git
cd 项目名
```

如果你还没有安装 Git，可以先使用 GitHub Desktop，或者让 AI 根据你的系统给出安装步骤。执行命令前，先确认命令的作用和目标目录。

### 4. Fork：准备参与开源协作

Fork 是在自己的 GitHub 账号下复制一份远程仓库，适合：

- 没有原仓库写权限
- 准备提交自己的修改
- 想保留自己的项目副本

常见流程：

```text
Fork 原仓库
    -> Clone 自己的副本
    -> 创建分支
    -> 修改并 Commit
    -> Push 到自己的仓库
    -> 创建 Pull Request
```

## 七、开源许可证：下载前必须看

许可证决定别人可以怎样使用、修改和再发布项目。不要只看“项目是公开的”，公开不等于没有使用限制。

### 常见类型的直观区别

| 许可证 | 直观特点 |
| --- | --- |
| MIT | 宽松，通常允许修改和商用，但要保留版权与许可声明 |
| Apache-2.0 | 宽松，并包含更明确的专利授权条款 |
| BSD | 宽松，具体义务取决于版本 |
| MPL-2.0 | 通常按文件层面要求公开修改部分 |
| GPL | 以更强的开源共享要求著称 |
| AGPL | 对网络服务场景的源码共享要求通常更严格 |

这是入门级说明，不是法律意见。商用、二次分发、混合多个许可证时，应直接阅读仓库中的 `LICENSE` 和相关文件，必要时咨询专业人士。

## 八、创建自己的第一个开源项目

### 最小文件结构

一个能被别人使用的项目，至少应该说明：

```text
your-project/
├── README.md
├── LICENSE
├── .gitignore
└── src/ 或 app/ 或 项目实际文件
```

### README 应该回答什么

建议按下面的顺序写：

1. 这是什么
2. 解决什么问题
3. 适合谁
4. 如何安装
5. 如何使用
6. 一个最小示例
7. 已知限制
8. 如何反馈问题
9. 使用了什么许可证

可以让 AI 先生成草稿，但要自己核对每个命令、路径和功能，不要把 AI 没有验证过的内容直接当成项目说明。

### 上传前安全检查

公开仓库前逐项检查：

- 密码
- API Key
- Access Token
- 云服务凭证
- 数据库连接串
- 私人照片和文档
- 内部域名、内网地址
- `.env` 文件
- 构建产物中的敏感信息

一旦敏感信息进入 Git 历史，仅仅删除当前文件通常不够，还需要撤销或轮换凭证，并清理历史记录。

### 发布版本

当项目达到一个别人可以安装和使用的状态时，可以：

1. 创建一个版本 Tag。
2. 编写 Release 说明。
3. 上传构建好的安装包。
4. 说明支持的系统、已知问题和升级方式。

不要把未经测试的压缩包标成正式版本。

## 九、用 AI 辅助 GitHub，但别把判断交出去

AI 适合帮助你：

- 把需求拆成搜索关键词
- 解释命令和报错
- 生成 README 初稿
- 把 Issue 整理成任务清单
- 检查文档是否缺少安装步骤
- 生成基础的 `.gitignore`

AI 不应该替你直接决定：

- 一个项目是否安全
- 一个许可证是否适合商用
- 一个命令是否可以在当前电脑执行
- 一个下载文件是否可信
- 一个仓库是否真的还在维护

推荐的工作方式：

```text
让 AI 给候选
    -> 回到 GitHub 原仓库核对
    -> 在隔离环境中试用
    -> 记录结果
    -> 再决定是否长期使用
```

## 十、常见误区

### 误区 1：Star 多就一定最好

纠正：Star 代表关注度，不代表安全、维护质量或适配你的需求。

### 误区 2：Public 项目可以随便拿去商用

纠正：先看许可证和第三方依赖的许可证。

### 误区 3：Fork 就等于下载到电脑

纠正：Fork 是远程复制，Clone 才是复制到本地。

### 误区 4：Pull Request 提交后就会合并

纠正：PR 是协作申请，需要维护者审核。

### 误区 5：删除密钥文件就安全了

纠正：密钥可能仍然留在 Git 历史中，必须立刻撤销并轮换。

### 误区 6：只看首页，不看最近更新

纠正：项目是否还维护，通常比 Star 数量更值得关注。

## 十一、零基础学习路线

### 第 1 阶段：会用

- 注册账号
- 搜索仓库
- 看 README
- 下载 Release
- 认识许可证

### 第 2 阶段：会管理

- 使用 Star 和 Watch
- 订阅项目更新
- 阅读 Issues
- 下载 ZIP 和 Clone
- 看懂版本发布说明

### 第 3 阶段：会协作

- Fork 项目
- 创建分支
- 提交 Commit
- 发起 Pull Request
- 根据反馈修改

### 第 4 阶段：会发布

- 创建自己的仓库
- 写 README
- 添加 LICENSE
- 清理敏感信息
- 创建 Release
- 维护 Issues

## 十二、快捷检查清单

### 下载别人项目前

- [ ] Issue 和反馈渠道可用。

## 结语

GitHub 的入门重点不是背完所有术语，而是完成一次真实的开源项目体验：

```text
找到项目
    -> 看懂项目
    -> 安全使用
    -> 提出问题
    -> 做出修改
    -> 分享自己的作品
```

AI 正在降低写代码和写文档的门槛，但真正可靠的结果仍然来自核对、测试和持续维护。零基础可以开始，谨慎和耐心会让你走得更远。
